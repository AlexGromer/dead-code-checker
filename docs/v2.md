# The graph checker (preview)

`dead-code-checker graph ...` is the second checker in this package: it builds a reachability graph of symbols and
reports what nothing reaches, where the v1 checker matches names as text. This page covers what exists today: where
data goes, how it is configured, the commands (`doctor`, `check`, `fix`, `view`, `why`, `tree`, `publish`, `prune`, `runtime`, `pages`,
`lock`, `index`, `cache go`), the viewer, the SARIF output, the engines (the analysis tools that confirm a dead claim), the library
behind the graph and the extractors of the languages. A language without an extractor is named in the output
(`dc.unsupported-language`), never skipped silently.

```console
$ dead-code-checker graph doctor [--root DIR] [--out DIR] [--jobs N] [--json] [--engines-dir DIR] [--lock FILE] [--all] [--versions] [--strict]
repo:      /home/me/src/app (app-1a2b3c4d)
data dir:  /home/me/dead-code-checker/data/projects/app-1a2b3c4d (chosen by: tool)
runs:      /home/me/dead-code-checker/data/projects/app-1a2b3c4d/runs
index:     /home/me/dead-code-checker/data/index.html
config:    none: mode closed_world, on, budget commit 20s branch 900s, viewer code on (6291456 bytes), 0 waive
runtime:   off
workers:   8
tool:      gitleaks: /usr/local/bin/gitleaks
tool:      graphviz-dot: /usr/bin/dot
tool:      bwrap: /usr/bin/bwrap
engines:   no lock: engines are used as found (--lock FILE pins them by sha256); engines dir: none (PATH only)
sandbox:   bwrap
go cache:  /home/me/dead-code-checker/data/caches/gomod (does not exist)
  basedpyright               missing      sem: python  not found on PATH; pipx install basedpyright  (or: python3 -m pip ...)
  vulture                    ok           audit,branch: python  /usr/bin/vulture
```

`doctor` writes nothing. Exit 0; 1 when the configuration has an error; 2 for a usage error, an `--out` inside the
repository, a lock that cannot be read, or when no data directory can be used (and with `--strict`, when an engine of the
repository's languages is missing, not in the lock or does not match it). The engine rows are described under
[Engines](#engines).

## Commands

```console
$ dead-code-checker graph check --scope branch|repo [--base REF] [--root DIR] [--out DIR] [--no-viz] [--plain] [--jobs N]
                                [--show-suspects] [--min-confidence N] [--format text|json|md|sarif] [--timing]
$ dead-code-checker graph fix --dry-run [--scope branch|repo] [--code CODE]... [--path GLOB]... [--root DIR] [--base REF]
                               [--verify [--host HOST [--user USER] [--port N]]] [--min-confidence N] [--json]
$ dead-code-checker graph view [--root DIR] [--out DIR] [--plain]
$ dead-code-checker graph why NODE [--root DIR]
$ dead-code-checker graph tree NODE [--root DIR] [--callers | --callees] [--depth N] [--width N] [--json | --svg [--out FILE]]
$ dead-code-checker graph publish [--root DIR] [--out DIR] [--gh-pages] [--dry-run] [--deny-file FILE]
$ dead-code-checker graph prune [--dry-run | --apply] [--keep N] [--days D]
$ dead-code-checker graph pages
$ dead-code-checker graph runtime [--root DIR] [--host HOST [--user USER] [--port N]] [--classes] [--json]
```

`check --scope branch` compares the work tree with the merge base of `HEAD` and its upstream (or `--base REF`) and reports
what the diff left dead. `check --scope repo` checks the whole tree as if every file had just been added: the codes are the
branch level's (`dc.introduced-dead`, `dc.dead-cluster`, ...) and every finding of the tree is pre-existing, so an error about the tree is
shown as a warning and nothing blocks. Exit 1 when a finding is an error, 2 for a usage or data-directory error, 0 otherwise; a check
that fails itself is one `dc.check-failed` warning and exit 0, never a traceback.

A dead claim that no index or engine of the language corroborates is a *suspect*: level I, `dc.suspect`, hidden from every output
unless `--show-suspects` (the pages and `findings.json` always have them). Until an engine layer plugs in, every dead claim is a
suspect, so use `--show-suspects` to see anything dead.

Every `check` and `view` stores its artifacts in `<data dir>/runs/<utc>-<scope>-<head8>/` (or under `--out`) and prints the
links: `index.html` (the whole graph), `change.html` and `change.svg` (the branch level: the subgraph of the diff), `modules.svg`
(the module overview), `graph.json.gz` (everything, also when a page was cut), `report.md`, `findings.json` and `sarif.json`. A
`latest` pointer names the newest run; the lens data of the viewer is also in the run's `lens/` folder. `--no-viz` writes none of them; `--plain` makes the pages carry their data without deflate
for a browser that has no `DecompressionStream`.

## The viewer

`index.html` and `change.html` are one self-contained file each: no network, no CDN, no `fetch`, a content-security policy that
forbids all of it, names and code reach the page through `textContent` only. The page has a treemap (directory, file, symbol), a
full-screen graph view with levels of detail and a minimap (`g`), an ego graph of one symbol, search (`/`, also `/regex/`), filters
by language, kind, module, root kind, verdict and edge tier, the why-alive path of a symbol (it is the parent chain the reach
computed, nothing is recomputed in the browser), the call tree (callers and callees) of the selected symbol and its code. A switch in the
header changes the lens over the same run (unused, duplicates, architecture, health: see [Viewer lenses](#viewer-lenses)). Colour is
never the only channel: the verdict word, a glyph and an outline say it too. A page above 24 MB, or a graph above 60 000 nodes, is
cut to what is not plainly alive, the roots, the marked nodes and a few hops around them; it says so (`dc.viz-truncated`) and
`graph.json.gz` has everything. Open `graph.json.gz` in the page with its file button.

**Code fragments** (the body of a symbol, at most 40 lines) are put into a page only when `gitleaks` is installed: one scan of the
files that hold the fragments, with the default rules and no configuration from the repository; a fragment with a finding is
replaced by a marker, and a scan that fails or runs out of time means no fragments at all, never unscanned ones. Without gitleaks the
pages show names only and one warning (`dc.viewer-code-off`) says how to get the fragments. A page that carries code says that it is
local (`<meta name="dc-local">`): do not publish it. `viewer_code = false` turns the fragments off without a warning;
`viewer_code_bytes` is their budget. `$DEAD_CODE_CHECKER_GITLEAKS` names the binary (an absolute path); else the system
directories, then `PATH`.

**Pictures**: `modules.svg`, `change.svg` and `tree --svg` are laid out by Graphviz `dot` when it is installed (`$DEAD_CODE_CHECKER_DOT`
or `PATH`), run without network when `bwrap` is available, and by a built-in layered emitter otherwise, with one warning
(`dc.graphviz-missing`) that says how to install it. A `dot` that fails or times out is a warning too.

## SARIF

`check --format sarif` prints one SARIF 2.1.0 document: the rules are the finding codes that occur, the results carry `level`
(error, warning, note), the message, the file and line (relative to the repository root, `%SRCROOT%`), the why in `properties.why`
and a fingerprint of code, path and message. It is sorted and has no clock and no absolute path, so two runs on the same tree give the
same bytes. `sarif.json` of a stored run is the same document with the suspects included.

## Publish

`publish` writes the architecture of the project as files you can commit: `docs/architecture/modules.svg`, `modules.drawio`
(opens in diagrams.net), `architecture.svg` (the layered module view of the architecture lens), `calls/NNN-name.svg` (what each entry point reaches), `index.md` and `.dc-digest`. They hold names, counts and
relations, never source code. The output is deterministic. Everything is rendered in memory and scanned first, by gitleaks and by a
built-in marker scan (private-key blocks, token shapes, `password = value`, e-mail and IPv4 addresses, absolute paths of a user's
machine, plus every word or regular expression in `--deny-file`); one finding and nothing is written (exit 1); no gitleaks is a finding too.
`--gh-pages` also commits the interactive page (no code fragments) to the **local** branch `gh-pages` in a temporary worktree and prints
the push command; nothing is ever pushed. `--dry-run` writes and commits nothing. `--out` stays inside the repository and no file is
written through a symlink. A branch check of a project that has published adds one `dc.publish-stale` warning when the files no longer
match the code.

## Prune and the overview page

`prune` lists the old runs of every project of the data root and the bytes they take (a dry run unless `--apply`): the last 10 runs
of each scope (branch, repo), every run younger than 14 days and the run `latest` points to are kept (`data/pages.json`; `--keep`,
`--days`). A run is also cleaned up this way, at most 20 per run, after each stored run. `pages` writes `<data root>/index.html`: one
row per project with its last branch run and last repo run, their error, warning and suspect counts and the languages; static, no
script, it opens from `file://`, it lists local paths and is not for publishing. Runs stored with `--out` are neither cleaned nor listed.

## Where data goes

Nothing is written into the analysed repository. A run keeps its data in the directory of the tool:

```
<tool dir>/data/index.html
<tool dir>/data/projects/<name>-<hash>/runs/        artifacts of each run
<tool dir>/data/projects/<name>-<hash>/store.sqlite
<tool dir>/data/projects/<name>-<hash>/ledger.jsonl
<tool dir>/data/projects/<name>-<hash>/layout-cache/   the layout of the graph view (a cache, deletable)
<tool dir>/data/projects/<name>-<hash>/repo.json, summaries.json   what the overview page shows
<tool dir>/data/caches/gomod                        the offline Go module cache (see Engines)
```

`<name>` is the directory name of the repository and `<hash>` the first 8 hex digits of the sha256 of its real path, so
two repositories called `app` do not share a directory. `<tool dir>` is the project directory of a git clone, an
unpacked release or an editable install (the directory that holds `pyproject.toml` next to the package). It is
`.gitignore`d in this repository.

The data root is the first of these that works:

1. `$DEAD_CODE_CHECKER_HOME`, when set. An explicit choice: if it is not writable that is an error, not a fallback.
2. `<tool dir>/data`, when it is writable and not inside the analysed repository.
3. `$XDG_STATE_HOME/dead-code-checker`, default `~/.local/state/dead-code-checker` (`%LOCALAPPDATA%\dead-code-checker`
   on Windows).

When step 2 is skipped (a package installed into site-packages, a system install shared by several users, a read-only
checkout, analysing the tool's own repository) one warning line says why and where the data goes instead.

`--out DIR` moves the run artifacts (`runs`) to DIR; the store and the ledger stay in the project directory. A DIR
inside the analysed repository is refused.

## Configuration

`.dead-code-checker.toml` in the analysed repository, table `[graph]` (the `[deadcode]` table belongs to the v1
checker and is not read here):

```toml
[graph]
mode = "closed_world"        # or "library": something outside the repository calls into it
viewer_code = true           # false: pages carry no source code
viewer_code_bytes = 6291456  # budget of the source text of a page

[graph.budget]               # seconds a level may run; the file cannot ask for more than 120 / 3600
commit_s = 20
branch_s = 900

[[graph.waive]]              # a finding code that a path (glob) or an engine may keep, until a date
code = "dc.dead"
path_glob = "legacy/*.py"
reason = "removed in the rewrite"
until = 2026-12-31
```

Switching the check off needs a reason and a date, and it expires:

```toml
[graph]
enabled = false
disabled_reason = "migration"
disabled_until = 2026-12-01
```

A valid disable is a warning on every run; after its date the check runs again (`dc.disabled-expired`). A waive past its
date is an error (`dc.waive-expired`). Unknown keys are errors. The file is read only when it is a regular file of at
most 1 MB inside the repository, and a repository cannot choose what runs or where data goes: a `path`, `paths`,
`argv`, `args`, `env`, `engines_dir`, `cmd`, `command`, `exe` or `binary` key is `dc.bad-config`.

`[graph.runtime]` (the runtime-signal mode, off by default) is a table of its own; see "Runtime mode: the target half" below.

Variables override the file; a wrong value is a warning and is ignored.

| Variable | Meaning |
| --- | --- |
| `DEAD_CODE_CHECKER_HOME` | the data root (above) |
| `DEAD_CODE_CHECKER_JOBS` | workers, default the CPUs, at most 8; `--jobs N` wins |
| `DEAD_CODE_CHECKER_MODE` | `closed_world` or `library` |
| `DEAD_CODE_CHECKER_VIEWER_CODE` | `1`/`0`, `true`/`false` |
| `DEAD_CODE_CHECKER_VIEWER_CODE_BYTES` | integer > 0 |
| `DEAD_CODE_CHECKER_BUDGET_COMMIT_S`, `..._BRANCH_S` | seconds > 0 (your own value, not clamped to the file ceilings) |
| `DEAD_CODE_CHECKER_RUNTIME_HOSTS` | comma-separated hosts a repository's `[graph.runtime]` may name (runtime mode) |

## Parallel units

Independent work (one unit per file, per package, per engine) runs through `dead_code_checker.graph.par.run_units`: a
`concurrent.futures` pool, results in the order of the units whatever finishes first, the same result for 1 and for N
workers, the first failing unit in order re-raised.

## The core graph (library)

The pieces below are in `dead_code_checker.graph` and can be used from Python; the commands (`doctor`, `check`, `fix`, `view`, `why`, `tree`, `publish`, `prune`, `runtime`, `pages`, `lock`, `index`, `cache go`) run them.

| Module | What it does |
| --- | --- |
| `model` | nodes, edges, roots, evidence, per-file facts, shards and findings, as plain tuples; the same graph in any input order has the same digest |
| `contracts` | the `Extractor` and `RootExtractor` interfaces and their registry: where a language pack plugs in |
| `langs` | file name, extension, shebang and content to language (`data/langs.json`) |
| `store` | the SQLite cache in the project's data directory: shards by content hash, snapshots, the graph |
| `vcs` | the repository: a snapshot with blob hashes, diffs, merge-base, file content through one `git cat-file --batch` |
| `roots` | what something outside the code runs or loads: systemd units, cron, `package.json`, html pages, extension manifests, tool configs, CI files, docs |
| `rootsrc` | the same for packaging and build files: `pyproject.toml`, `setup.cfg`, Cargo, `.csproj`, Gradle, Maven, Dockerfile, Makefile, justfile, compose |
| `classreg` | classes that registration files name: `META-INF/services`, `module-info.java`, Spring factories, `web.xml` |
| `link`, `xlink` | per-file facts to the symbol graph: scopes, imports, inheritance, the tiers S/T/N/D, cross-language edges (paths, native symbols, variables) |
| `reach` | what the roots reach: alive, weak-alive, test-only, doc-only, dead, dead-cluster, public-unused |
| `verdict` | a dead claim is a warning only when an index or an engine agrees; else a hidden `dc.suspect` (level I) |
| `levels` | the branch level (what a diff added and left dead, what it orphaned), the graph build, `why` |
| `tree` | the callers and callees of one symbol, as text, JSON or an SVG picture |
| `report`, `sarif` | findings as text, JSON, markdown and SARIF 2.1.0, each with a why |
| `repo` | the repo level of `check`: the whole tree as if every file were added |
| `viz`, `layout` | the data pack of a graph, the one-file page (`viewer/`), the SVG pictures, the deterministic layout of the graph view |
| `snippets` | the code fragments of the pages, behind the gitleaks scan |
| `artifacts`, `pages` | where a run is stored, the cleanup of old runs, the overview page |
| `publish` | the architecture as files, the scan before they are written, the local `gh-pages` branch |
| `engines`, `proc`, `sandbox` | the analysis tools: the registry, the lock, finding an engine, doctor and the plan; starting a process in its own group; bubblewrap or no sandbox |
| `adapters` | what an engine says (ruff, vulture, go-deadcode, staticcheck, knip, rustc and cargo, pmd, tsc, ...) as evidence on graph nodes |
| `jobs`, `gocache` | the jobs of a plan over a tree, run in parallel; the offline Go module cache |
| `sem`, `semcache`, `semuse`, `semindex` | the semantic layer: SCIP indexes and language servers; the cache of their results in the store; its use by the levels; `graph index` |
| `steps` | the two seams of `levels.Steps` filled: the semantic cache and the engines for the branch level |
| `confidence` | the number 0..100 of a dead claim, a second axis that never changes a verdict (`data/confidence.json`) |
| `lens`, `extract/bodyhash` | the data of the viewer lenses (unused, duplicates, architecture, health) and the body hash that finds duplicates |
| `fix`, `fixverify`, `pycheck` | the removal patch for review, and the checks of it on a copy of the tree |
| `runtime`, `rttransport`, `rtcfg`, `rtbox` | the runtime-signal mode: the tests under a tracer on a configured ssh host, the stored run, what a claim about a symbol that ran becomes |
| `cli` | the commands |

Language support is data plus an extractor: `langs.json` says which module reads a language, and until that module exists a
changed file of the language is one `dc.unsupported-language` warning, never a silent skip. The roots and the linker work on
facts, so they run for any language that has an extractor.

The two seams of the levels, `levels.Steps(semantic=..., prove=...)`, are filled by `steps.default()`; without them every dead
claim of a diff is a suspect. The corroboration rule (`verdict`) says which engine may confirm what.


## The extractors

An extractor reads one file and returns its facts (definitions, references, imports, roots, dynamic sites); it never reads the
path, runs nothing and does not depend on the order of anything, so the result is cached by the content hash of the file. The
module that reads a language is named in `data/langs.json`.

| Module | Languages | Needs |
| --- | --- | --- |
| `py` | Python | nothing (stdlib `ast`) |
| `ts_generic` | shell, Go, Rust, JavaScript, TypeScript, TSX, Java, Kotlin, C, C++, C#, Lua, Ruby, PHP, Scala, Groovy, Nix, Starlark, HTML, Vue, Svelte | tree-sitter |
| `cfg` | YAML (Kubernetes, Helm values, GitHub Actions, GitLab CI, compose, Ansible), Helm templates, HCL (Terraform) | nothing; tree-sitter for HCL and, optionally, Helm templates |
| `cfgts` | Makefile, justfile, Dockerfile, nginx, jsonnet | tree-sitter |
| `cfgconf` | HAProxy, keepalived, Grafana Alloy, Redis, LogQL | nothing (line and token scanners) |
| `tpl` | Jinja2 templates | tree-sitter |
| `schema` | SQL, protobuf, GraphQL | tree-sitter |
| `pwsh` | PowerShell | PowerShell 7 (`pwsh`) |

The queries that turn a parse into facts are data, one directory per grammar (`data/queries/<grammar>/{defs,refs,roots,...}.scm`),
with the per-language rules next to them (`rules.json`); a language is added by data, not by code.

The tree-sitter extractors are an optional extra:

```console
$ pip install 'dead-code-checker[treesitter]'     # tree-sitter, tree-sitter-language-pack
```

Without it the other extractors work and each tree-sitter language is one `dc.degraded-extractor` warning (its files are not in
the graph, and the message says what to install); nothing falls back to a guess and nothing crashes. Tested with tree-sitter 0.26.1
and tree-sitter-language-pack 1.25.0. That pack version fetches a grammar that is not on disk from the network when it is asked for
one, so the loader asks only for grammars the pack lists as downloaded; a grammar that is not there is a missing grammar, with the
command that fetches it:

```console
$ python3 -c "import tree_sitter_language_pack as p; p.download(['go', 'bash'])"
```

A pack that cannot say what is on disk (it has no `downloaded_languages()`) is treated as having nothing there, so the default stays
without network whatever the version of the pack is; `DEAD_CODE_CHECKER_TS_DOWNLOAD=1` lifts both limits.

| Variable | Meaning |
| --- | --- |
| `DEAD_CODE_CHECKER_TS_CACHE` | the base directory of the language pack's grammar cache |
| `DEAD_CODE_CHECKER_TS_DOWNLOAD` | `1`: let a run fetch a missing grammar itself (the only network access of an analysis; off by default) |
| `DEAD_CODE_CHECKER_PWSH` | the PowerShell 7 executable, else `pwsh` from `PATH` |

PowerShell is read by the PowerShell parser itself in one long-lived `pwsh -NoProfile -NonInteractive` process per worker. It
parses text and never runs it, but it is an ordinary process of yours: there is no sandbox around it.

A file that cannot be read is one file error and never a lost run: a syntax error, an input nested deeper than the recursion limit
(a hostile `a: [[[[ ...` of YAML, a deep expression of Python) and a missing grammar each cost the facts of that file only.

Generated code is not reported. A schema file whose header says that a generator wrote it, and a vendored or generated schema path
(`google/protobuf/`, `vendor/`, ...), are left out of the graph; in the code languages a definition between the lines `// BEGIN GENERATED`
and `// END GENERATED` (or `// <generated>` and `// </generated>`) is flagged generated, so a member of a copied-in library that the
file does not use is reported by nobody. The marker pairs are data (`data/generated.json`, `blocks`): add the pair your generator
writes.

The facts of the languages also carry the cross-language edges: a command a call or a shell line runs (`exec`), a string that
spells a path (`lit`), a native symbol (`ffi`), an environment variable or configuration key written in one language and read in
another (`env`), and the tables, messages and GraphQL fields that code or a schema file names (`schema`). They are weak by
construction: such an edge can keep a symbol alive, it can never make a finding.

## Engines

A dead claim of the graph is a warning only when something else agrees: a semantic index (SCIP) that covers the package, or an
engine of the language that names the very symbol (go-deadcode, rustc and cargo `dead_code`, knip, PMD, Roslyn, vulture at
100 percent; `data/verdict.json` says what each may confirm). The engines are ordinary tools you install yourself; the checker
never installs, downloads or updates one, and never gives one the network.

### Where an engine is found, and whether it is trusted

An engine is looked for in the engines directory first (`--engines-dir DIR`, or `$DEAD_CODE_CHECKER_ENGINES_DIR`; several
directories are separated like `PATH`) and then on `PATH` (`--no-path` leaves `PATH` out). Only absolute entries of `PATH` are searched, and only they are handed to a started engine or tool: a relative one (`.`, `bin`, an empty entry) would be looked up from the working directory, which is often the analysed repository, so a planted `cp`, `go`, `tsc` or engine there is never found. The same holds for every program the tool starts by name (`git`, `ssh`, `bwrap`, `unshare`, `dot`, `gitleaks`): it is looked up in the absolute entries only and started by its absolute path (`dead_code_checker/safepath.py`). The repository's own configuration
cannot choose a path, an argument list or an environment of an engine.

Without a lock the engines are used as found (`doctor` says so). With `--lock FILE` (or `$DEAD_CODE_CHECKER_ENGINES_LOCK`) an
engine runs only when its file has the pinned sha256:

```json
{"schema": 1, "platforms": {"linux-x86_64": {"engines": {"vulture": {"sha256": "<64 hex digits>", "version": "2.14"}}}}}
```

| Status | Meaning |
| --- | --- |
| `ok` | found (and, with a lock, the pinned bytes; a PowerShell module is pinned by the hash of its whole directory tree) |
| `missing` | not found; `doctor` prints the install hint of this OS |
| `untrusted` | a lock is in use and does not list the engine |
| `sha-mismatch` | a lock is in use and the file is not the pinned one (a copy earlier on `PATH` does not hide the pinned one) |
| `degraded` | the engine has no build for this OS |

`dead-code-checker graph lock --out FILE [--engines-dir DIR] [--no-path] [--lock OLD]` pins every engine found now for this
platform (and keeps the other platforms of `OLD`). A lock that was asked for and cannot be read is an error, never "no lock". An
engine that is missing, not pinned or degraded is one warning `dc.engine-incomplete` with the install hint, once per engine; it
never blocks.

What a lock does and does not promise: it pins the bytes of the engine (or the tree of a module), nothing else. It is checked
when the engine is looked for, and the engine is started later by its path, so a file replaced in between is not caught (a
local race, not a network one). It says nothing about what the engine then reads: knip, tsc, tflint, staticcheck, go-deadcode and
ruff run in a private copy of the repository's files (below) and read the configuration in it, and some of those files can run project code
(a `knip` or `tsc` plugin, a build script). Only the engines that build the project and the indexers go through the sandbox
below; run the checker on a repository you would build anyway, or in a container, when you do not trust its configuration.

With a lock, a file is never started before its bytes are checked: the one probe that runs a candidate to tell what it is (the
bare `deadcode` is the Go tool only when its `-h` says Go) sees only the files that have the pinned sha256. `graph lock` and a run
without a lock do start it once with `-h`. The lock covers the engines of the registry. The tools around them are looked up on
`PATH` and run unpinned: `go` (the offline Go cache check runs `go list` and `go mod edit` in a scratch copy of `go.mod` and
`go.sum`, with `GOPROXY=off`), `git`, and `bwrap` or `unshare` for the sandbox and the network-less run. Keep the absolute entries of `PATH` to
directories you trust.

The version that stamps an engine's results (the semantic cache, the text "corroborated: vulture@2.14 ...") is the lock's, else
what the engine's version command says, else a digest of its file, so an upgraded engine invalidates what it produced.

### The sandbox

An engine that builds the project (`cargo check`, the SCIP indexers) executes project code. It runs in bubblewrap when `bwrap`
is installed and works: no network, the whole file system read-only (the repository included), a fresh `/tmp`, private scratch
directories for its output. Without bubblewrap it runs with no network when `unshare -rn` works, else unsandboxed; either way one
warning `dc.sandbox-weak` says so. Nothing is refused for lack of a sandbox. `doctor` shows the mode.

### The analysed tree is never written

Every engine job runs in a private copy of the files it analyses, made in the job's scratch directory and deleted with it: the
files the checker sees (tracked and new, no symlinks, nothing git ignores), all of them for a job at the root and for a job in a
subdirectory too (a Cargo workspace member, a Go module of a `go.work` or with `replace ../x`, a Cargo path dependency and a
tsconfig `extends` or `references` reach into the sibling directories, so the whole tree is there), only the named files for a job
over a list of files. A `Cargo.lock` that cargo resolves again, a `tsconfig.tsbuildinfo`, a cache, `__pycache__` or anything else
an engine writes lands in the copy. The engine's output is translated back, so a path it prints in the copy is the path in the
tree. `cargo` is not run with `--locked` (a library without a `Cargo.lock` would not build); its lock is written into the copy.
Python engines also run with `PYTHONDONTWRITEBYTECODE=1`. The output of an engine (`{out}`) is a private directory outside the tree
as well.

The directories git ignores and an engine reads, `node_modules` and `.terraform` (those of the job's directory and of the
directories above it; the dependencies of a sibling directory are not in the copy, so a project reference into a sibling whose
dependencies are not hoisted does not resolve them), are not copied whole (they can be gigabytes): the copy holds directories of
the same shape whose small files (up to 128 KiB) are copies and whose larger files are links to the real ones. A dependency is
read, and a file or directory an engine creates there, or a small file it rewrites in place, stays in the copy. One case reaches
the real tree: an engine that rewrites a large dependency file (over 128 KiB) in place, when no sandbox holds the tree read-only
(every engine that does not build the project, and a run without bubblewrap); none of the engines of `data/audit.json` does.
A tree that cannot be copied (no space, a copy that takes over ten minutes, a dependency directory of over 400 000 entries) is a
failed job, `dc.engine-incomplete`; the engine is not started in the tree instead. The language servers already ran on a scratch
copy.

What this costs: every job has its own copy, so a run needs the size of the tree (and of the small dependency files) in free
space in the temporary directory times the number of jobs that run at the same time (`--jobs`, `DEAD_CODE_CHECKER_JOBS`), and its I/O times the number of
jobs: a repository with many Go modules or crates runs each module's job over the whole tree. There is no size limit, only the ten
minutes of the copy; on a large repository lower `--jobs`, or point `TMPDIR` to a fast disk with room. On Windows the links need
a privilege (developer mode or an administrator): without it the large dependency files are copied too, which is slower and can run
into the same limits.

### What runs

`data/audit.json` says how each engine is called (`vulture`, `ruff`, `shellcheck`, `go-deadcode`, `staticcheck`, `knip`, `tsc`,
`cargo`, `pmd`, `detekt`, `tflint`, `cppcheck`, `deadvalues`, and the SCIP indexers `scip-python`, `scip-go`, `scip-typescript`,
`scip-dotnet`, `scip-clang`, `rust-analyzer`); `data/engines.json` says which engine serves which language in which role
(`branch`: asked about the dead symbols of a diff; `audit` and `sem`: run over the whole tree by `graph index`). The output of
each engine is read by `data/adapters.json`, one format per tool, each checked against a recording of the real engine in
`tests/fixtures/engines`; output of another shape is `dc.engine-output`, never an empty result. Engines of one plan run in
parallel (`--jobs`); the result does not depend on the number of workers. An engine in the plan with no entry in `audit.json`
is named once (`dc.engine-unwired`); the language servers of `data/sem.json` are run by the language-server step instead.

`dead-code-checker graph index [--root DIR] [--only a,b] [--timeout S]` runs the indexers and engines over the whole tree and keeps
the results in the store under the hash of the files they were made from: an index as `sem:<engine>:<root>:<hash>`, the matches
of a tool as `eng:<tool>:<hash>`. A run is incremental (a job whose files and engine are unchanged is not run again) and the
levels use what the cache holds without running an engine: SCIP overlays refute name edges that an index resolved otherwise and
corroborate the packages they cover; the matches corroborate exact claims. A stale or foreign item is not applied and one
warning says so.

On the branch level, `steps.prove` asks the `branch` engines about the dead symbols of the diff that nothing corroborates yet and,
still unproven, the language servers (a scratch copy of the tree, 20 queries and 20 seconds at most per language, `data/sem.json`):
a reference a server finds makes the symbol alive; a server that finished indexing and found none corroborates the claim, unless
a framework may call the symbol by name (a handler such as `http_open`). `DEAD_CODE_CHECKER_LSP=off` switches the servers off.

### The offline Go module cache

go-deadcode, staticcheck and scip-go load a module with its dependencies and never reach the network (`GOPROXY=off`), so without
the dependencies in a module cache they fail and the Go claims stay suspects. The cache is `--go-cache DIR`, else
`$DEAD_CODE_CHECKER_GO_CACHE`, else `<data root>/caches/gomod`; the process's own `GOMODCACHE` is never used. It is usable when it
exists and is not empty, and is only read. `dead-code-checker graph cache go --check REPO...` lists the modules it lacks (no
download: `go list` runs on a copy of `go.mod` and `go.sum`), `--fill` prints the commands that fill it, to be run where there is
network access. An engine run without a usable cache goes ahead, and the warning of a failed run names the reason.

### Not here yet

`cargo clippy` and the JVM call-graph engine (SootUp) are not run; `rustc` is listed by `doctor` but cargo is what runs for Rust.
The editor and session hooks, the nightly audit and its remote execution are not part of this tool. The runtime mode (`graph runtime`) is the only thing that talks to another machine, and only to one ssh host you configure and allow.

## Precision rules for dead-cluster claims

A dead claim on a symbol whose neighbours are all dead too (a dead cluster) is only as good as the roots and edges the checker
knows. Five generic rules remove the false claims of that kind that real trees showed. Each is data first (`graph/data/`) and has
a limit that is stated here.

**Ansible plugin classes.** A class that a framework builds by its name and calls by contract (`FilterModule.filters()`,
`LookupModule(LookupBase).run()`, `ActionModule.run()`, callback, inventory, vars, cache, connection, become, shell and strategy
plugins, `ModuleDocFragment`) is a hard root together with its contract methods; what `filters()` hands out is used through it.
The table is `py_class_roots` in `data/frameworks.json`. The Python extractor sees the text alone, so the linker keeps these roots
only for a file that is a plugin: a directory of its path matches `*_plugins` or `plugins`, or the file imports `ansible` or
`ansible_collections` (an absolute import). Any other file with a class of that name and method is no plugin and gets no root.
Limit: a plugin that sits in neither a plugins directory nor imports ansible (a path set only in `ansible.cfg`) is not rooted.

**Copy twins.** A file that sits under another root with the same relative path and the same facts as another file (an overlay,
a deploy payload, a vendored copy) is the same module: which of the two a dotted import loads depends on `sys.path`, which the
tree does not say. Their defs keep each other alive (an N edge, rule `copytwin`), and two dead copies are dead together. The flag
is `copy_twins` in `data/langs.json` (Python only). Limit: the facts must be equal, so a copy that differs by one line is another
module; a path that does not end with the other path is no copy; at most 24 files of one name are compared.

**Go: a value handed to another package.** `dep.F(T{})` and `dep.F(&T{})`, where `dep` is an imported package, hand a value of `T`
to code the tree does not contain, which may call it through an interface the tree does not declare (a logger, a handler, a codec).
The exported members of `T` stay used (a dynamic site `members:T`, tier D). Unexported members do not (another package cannot call
them), and a `T` that the tree does not declare keeps nothing. A receiver that is a local value (`obj.Do(T{})`) makes no site: the
callee is in the tree and its interfaces are matched by name. Limit: only a literal in an argument counts, not a variable of that type.

**Shell: a command word with a literal prefix.** `"check_$t" args`, `check_${t}` and `"run_${a}_post"` name a function by its
prefix: the glob `check_*` (tier D) makes every function of the family whose name starts with the prefix used. A prefix shorter
than 3 characters, or with a character no function name has (a path such as `"$D/tool"` or `/x/$y`), makes no site; a bare `$cmd`
keeps its own site. Limit: the match is by name over the whole shell family, not by file.

**JavaScript and TypeScript: top-level statements.** A call statement at the top level of a file (`main();`, `main().catch(..)`,
`(async () => { .. })();`, `await run();`) or an `if (require.main === module)` / `if (import.meta.main)` guard makes the file a
script: a soft `main` root on the file, so what the statements call is used. A test file and a package index (`index.js`,
`index.ts`, `index.d.ts`) are no scripts, because a test framework or an `import` runs them and nobody runs the file; a `package.json`
`main` or `bin` (or an npm script) that names an index roots it like any file. The statements of an inline script block of a page or
component are the page's own and make no `main`. Limit: an assignment (`const x = build();`) and a call inside a function are no
statements that run the file.

## Confidence

Every dead-symbol claim (`dc.dead`, `dc.dead-cluster`, `dc.introduced-dead`, `dc.orphaned-by-branch` and the `dc.suspect` that
stands for one of them) carries a number from 0 to 100 next to its level and code: how sure the checker is that the symbol is
really unused. It is a second axis. It is a deterministic sum over facts the run already holds, and the table of weights is the
data file `graph/data/confidence.json`, where each factor is explained:

- the base of the claim: a symbol of the graph 40, a member of a dead cluster 30 (a suspect takes the base of the code it replaced);
  the syntactic graph sees no types, reflection or framework conventions, so the base stays under 50;
- plus the independent corroborations (a semantic index, a compiler, another engine, a language server), the strongest first, the
  second counting half and the third a quarter, capped at 45 together: more sources never lower the number;
- plus the share of an engine's own confidence for its hit on the symbol (vulture reports a percent), also when it was below the bar
  that makes an engine hit a corroboration;
- minus hazards: the symbol is decorated, dynamic, an override or a protocol member (something outside the code may call it), and
  every distinct dynamic call site (`getattr`, reflection, `eval`, string dispatch) of its module, down to a floor;
- minus gaps of coverage: a language of the same family or another one has no working extractor here, or the graph has no hard
  production root of the language of the symbol, so part of the callers is not in the graph;
- plus or minus a runtime result when a caller supplies one (`confidence.annotate(..., runtime=...)`: a symbol that ran is a heavy
  penalty, a covered file whose symbol never ran a small bonus). A plain `check` gives none, so it changes nothing.

The note under a finding names the sum, for example `base 30, sources s-tier +25 = 55`. The number never changes a verdict: not the
level, the code, the message, the why, the order findings are sorted in, the exit code or what is hidden by default (a suspect with
a high number is still a suspect, and a number alone corroborates nothing). Nothing in the module can fail a check; a finding that
makes no dead-symbol claim has no number.

Where it shows:

- text and markdown print `confidence 55/100 (base 30, sources s-tier +25 = 55)` under the finding; JSON has `confidence` and
  `confidence_note`; `findings.json` and `report.md` of a run have it too;
- SARIF has `properties.confidence`, `properties.confidenceNote` and the result's `rank` (the same number as a float, so a code-scanning
  service can sort by it); the document stays byte-stable;
- the pages list the findings with a badge (`[55]`) in front of the code and have a sort control, "severity" (the order of the run,
  the default) or "confidence" (the surest claim first; a finding without a number goes last).

`check ... --min-confidence N` (an integer 0 to 100; anything else is a usage error, exit 2) leaves the claims whose number is under
`N` out of the printed text, JSON, markdown or SARIF and says how many (`3 finding(s) below confidence 31 hidden, --min-confidence`,
JSON `meta.below_confidence_hidden`). It is a display filter: the exit code, `findings.json`, `report.md`, `sarif.json` and the pages of
the run keep every finding, and a finding without a number is never left out.

## Viewer lenses

The header of a page has a switch of four lenses over the data of ONE run; nothing is computed in the browser and nothing leaves it.

| lens | shows |
| --- | --- |
| unused | the colouring of the graph as before (dead, dead-cluster, suspect, weak-alive, alive, ...); it needs no extra data |
| duplicates | groups of functions and methods whose bodies are the same after normalisation: comments, whitespace, the symbol's own name and the names of locals and parameters do not count, a constant, an operator, a called name or a decorator does. Groups are ranked by the duplicated mass (body size times copies minus one); each member shows its verdict word and a `[test]` mark; a click selects the symbol. Filters: hide tests, only groups with an unused copy, a minimum size, a text. |
| architecture | the modules (a directory cut to `arch.depth` path segments) in layers by dependency: a module uses the ones below it. A strongly connected set of modules is a cycle (outlined red, listed under the picture), an edge between two languages is dashed, the fill is the share of dead symbols. A click on a module draws its dependencies and fades the rest, and the side panel lists what it uses and what uses it. |
| health | a table of modules, worst first: a score from 0 to 100 and a grade (good, fair, poor, bad), symbols, lines, fan-in, fan-out, the dead and duplicate shares, in a cycle or not. The side panel of a row shows what the score is made of. |

The score of a module is `100 * (1 - sum(weight * penalty))` with penalties in 0..1: dead share (dead, dead-cluster and suspect
symbols), duplicate share, fan-out over `fan_cap`, in a cycle, symbols over `size_cap`. A module with fewer than `min_symbols`
symbols is listed but not graded. The formula, weights and grades are in the data file, so the lens states its own arithmetic.

**Files.** A run directory with the lenses has `lens/lens-arch.json.gz`, `lens-health.json.gz`, `lens-dup.<n>.json.gz` and
`lens-manifest.json.gz` (the chunk names and the summary). Whole chunks, in the priority architecture, health, duplicates, up to
`inline_bytes` of data ride inside the page itself and are inflated when a lens is first shown. What did not fit is named in the
page (`meta.lens.left`); the page cannot read a file next to it (its policy forbids it), so such a lens shows a button, "choose lens/
folder", that takes the folder once. A page opened from `graph.json.gz` has the lens summary but not the chunks and asks for the folder
the same way. A stale chunk of an earlier run in the same `lens/` folder is removed when a run is written there, a file that is not
ours is left alone, and the folder goes with the run when old runs are pruned. A lens that cannot be computed or written is a lens
that is off with its reason (`meta.lens.reason`; `dc.viewer-lens-off` for a write error): the page, the report and the exit code are
not affected. The architecture lens also goes into `publish` as `architecture.svg`, names and counts only, under the same scan.

**Limits and knobs** (`dead_code_checker/graph/data/lens.json`; every cut is counted in the summary, never silent):

- `dup`: `kinds` (func, method), `store_min` (extractors keep a body hash from this size: ast nodes for Python, tokens for the other
  languages), `min_size` per language (a group needs bodies of at least this size), `min_group`, `max_groups`, `max_members` listed
  per group, `max_body` (a larger body has no hash: a generated blob is no duplicate). Generated files are left out.
- `norm`: the comment syntax per language, where a parameter name stands (name first or type first), the declaration words after which
  an identifier is a new local. Names the normaliser does not see as locals stay as written: two bodies that differ only in those are
  not reported, so a missed duplicate is possible, a false one is not.
- `arch`: `depth`, `min_nodes` (a smaller module is folded into its parent directory), `max_modules` and `max_edges` (the page lists
  the largest modules and the heaviest edges), `edge_kinds` (empty: every kind is a dependency).
- `health`: `weights`, `fan_cap`, `size_cap`, `min_symbols`, `grades`. `inline_bytes` and `chunk_rows` cap the page blob and a chunk.

Editing the file changes the extractors' facts (the body hash is part of the shard key), so the cache is rebuilt for the files it
touches; it is read at start, there is no key for it in `.dead-code-checker.toml`.

**Which languages have duplicate detection.** Only a language whose extractor keeps a body hash: Python (by `ast`) and every
language read through the tree-sitter queries (shell, Go, Rust, JavaScript, TypeScript, TSX, Java, Kotlin, C, C++, C#, Lua, Ruby,
PHP, Scala, Groovy, Nix, Starlark; HTML, Vue and Svelte through their scripts), from the text of the definition node, so a language
needs no extra query for it. Bodies of different languages never group. PowerShell, the config languages and the schema languages
keep none: the duplicates lens does not look at them and says which languages it did look at (`meta.lens.dup.langs`). Without the
per-file facts (the shards of the cache could not be read) there is no duplicates lens and the page says why; the architecture and
health lenses need only the graph. A page cut to its smallest form (no evidence, no why texts) and every publication page carry no lens
data.


## Runtime mode: the target half

Static analysis says what nothing reaches; the runtime-signal mode adds what actually ran. The project's tests (or a command you
configure) run UNDER A TRACER on ONE separate machine, an ssh host you name, inside a bubblewrap box there, and only the set of symbols
that ran comes back. A symbol that ran is never reported dead; a symbol that did not run adds nothing (a test suite never covers
everything, so absence of a hit is no evidence). This section covers the configuration and the half that runs on that machine
(`graph/rtbox.py`); the part that copies the project over, starts it and reads the answer is described with its command.

### Trust model, in plain words

- **Nothing in this tool ever executes project code on the machine it runs on.** The mode needs a second machine; without one the step
  is a single line (`runtime mode: no execution target (...)`) and nothing runs.
- You choose the machine. The configuration file lives in the repository you analyse, which may be somebody else's, so a host named
  there is used only when you also allow it: list it in `DEAD_CODE_CHECKER_RUNTIME_HOSTS` (comma-separated), or pass the host on the
  command line yourself. Without that, the file's host is ignored and `doctor` says `not allowed`.
- You approve a host, not a login. Who the tool logs in as, and on which port, never comes from the repository's file (`user` and `port`
  there are ignored, with one `dc.bad-config` note): it comes from `--user` / `--port`, from your own entry `user@host:port` in
  `DEAD_CODE_CHECKER_RUNTIME_HOSTS`, or from your ssh configuration.
- The command in the file is data for that machine. It is split into words (like a shell would, but no shell is involved: no pipes,
  no `&&`, no expansion) and runs there only, inside the box. It is never run here, so the rule that a repository's `[graph]` table
  cannot name a `command` stays as it was; the `command` key of `[graph.runtime]` belongs to this table and means something else.
- The machine you run the checker on is refused as a target (loopback and its own names and addresses): there is no `local` target.
- What the box holds is the tracked files of the project at `HEAD` and nothing else of yours: no network, no home directory, no
  credentials. What comes back is a list of symbols (language, file, name, line, hit count); no output of the project and no file
  content, except one error line of a check run, with secret-looking parts masked.

### Configuration

```toml
[graph.runtime]
enabled = true                       # default false
host = "ci-box"                      # an ssh destination, or an alias from your own ~/.ssh/config
command = "python3 -m pytest -q"     # a string or a list of strings; default per language (below)
timeout = 900                        # seconds for all runs together, at most 1800
refresh_days = 7                     # a stored run older than this is run again
```

Unknown keys and wrong values are `dc.bad-config` warnings. A `host` that is empty, longer than 253 characters, starts with `-` (it
would be an ssh option), or holds anything but letters, digits and `. - _ : [ ]` (no whitespace, no control character, no `@`) leaves the
whole mode off. A wrong `command`, `timeout` or `refresh_days` falls back to its default. `user` and `port` are known keys that are never
read: one note says they are ignored, because a repository's file does not choose the login (see above). `doctor` prints one `runtime:` row (off, or the host and whether it is allowed) and contacts nothing.

### The target machine needs

Python 3.9 or newer, bubblewrap (`bwrap`) and `prlimit`, both from a root-owned system directory (`/usr/bin`, `/usr/local/bin`, `/bin`),
and the project's own test tools. The tool ships `rtbox.py`, the data file and the python tracer inside the delivery, so nothing of this
package is installed there; `rtbox.py` is one standard-library file that runs as `python3 -I rtbox.py --on-target --box DIR --sha256
HEX` from the delivery directory, and refuses to start without `--on-target`.

### The box

Every command runs in a bubblewrap box: all namespaces unshared (no network, loopback included), the file system read-only except the
private copy of the project, its HOME, TMPDIR and output directory, a fresh `/tmp`, the daemon sockets of the host masked (`/run`, the
real home, other unix sockets), the environment cleared to `PATH`, `HOME`, `TMPDIR`, `LANG` and what the tracer needs. `prlimit` caps the
CPU time, address space, file size, open files and processes (a language may lift the address-space cap and bound its heap another way),
and a wall clock covers all commands together; the process group is killed when it ends. Output is capped. If bubblewrap or `prlimit`
does not work on the target, nothing runs: the answer is the one line `no sandbox` with the reason. Commands run one after the other
(they share one writable copy and one clock).

### Tracers per language

| Language | How | Default command |
| --- | --- | --- |
| Python | a shipped `sitecustomize` (`sys.monitoring` on 3.12+, `sys.setprofile` before) records the first call of each function in every Python process of the command, children included; module and class bodies do not count | `python3 -m pytest -q -p no:cacheprovider` |
| JavaScript | `NODE_V8_COVERAGE`; a function counts when its first range ran | none: say the command |
| Go | `-coverprofile` is added after `go test`, then `go tool cover -func`; a command that is not a plain `go test` is `no tracer for go` | `go test ./...` |

TypeScript is not traced (source maps are not applied), and Java, Kotlin, Rust, C# and C or C++ have no tracer: such a language is one
`no tracer for <lang>` line, never a guess. A command that does not suit a tracer (for example `make test` for Go) is reported the same way.

### Limits and what comes back

Per run, at most 16 GiB of address space, 3600 CPU seconds, 1 GiB per file, 8192 open files, 2048 processes; 1800 seconds of wall clock
for everything. The project copy is limited to 256 MB, 16 MB per file and 100000 files, and symbolic links that leave the tree are
refused. The answer is `out/runtime.json` (status, one record per run with its exit code and tracer outcome, the executed symbols, and
for each file the blob id it was seen in, so a later change to the file makes the hit stale) and `out/manifest.json` (its size and
sha256). At most 300000 symbols come back; a longer list is cut by file and line, with a note. All limits are data in
`graph/data/runtime.json`.

## Runtime mode: the controlling half and `graph runtime`

```console
$ dead-code-checker graph runtime [--root DIR] [--host HOST [--user USER] [--port N]] [--classes] [--json]
```

`runtime` runs the whole round trip of the runtime-signal mode (the half that runs on the target is described above): it picks the one
execution target, makes the project copy, sends it, starts the box, pulls the answer, checks it and stores it. It prints one short
summary (`--json`: status, line, level, stored directory, symbol count, notes). `--classes` prints which checks of each language execute
project code (target only) and which only read it, and needs neither a target nor a repository. Exit 0 for a run, for a skip and for a
run that failed (it never blocks); 2 for a usage error (no repository) and for a project that has not opted in (`enabled = true`, or
`--host HOST` for this one call).

### Which machine

The host is `host` of `[graph.runtime]`, or the one given with `--host`. Three rules decide whether it may be used, in this order:

1. **Not this machine.** Loopback and unspecified addresses, `localhost`, this machine's host name and FQDN, any of its interface addresses
   and any name its `/etc/hosts` maps to those are refused, whatever the list or the command line says. Nothing is looked up in the DNS.
   An alias that only your ssh configuration maps to this machine is yours to get right.
2. **You allowed it.** A host that only the repository's file names is used when it is in `DEAD_CODE_CHECKER_RUNTIME_HOSTS`
   (comma-separated entries `[user@]host[:port]`; an IPv6 host with a port is `[::1]:22`). `--host HOST` skips the list (you named the host
   yourself) but not the other rules, and `HOST` must still be a plain ssh destination (no leading `-`, no whitespace). The login is
   yours as well: `--user` and `--port` win over the `user@` and `:port` of your entry for that host, and where neither is given your ssh
   configuration decides; the repository's file has no say.
3. **Its host key is already known.** The tool never accepts a new key: `ssh` runs with `StrictHostKeyChecking=yes`, so the key has to be in
   your `known_hosts` (connect once by hand to put it there). A host that fails the check is one skip line saying so.

With no usable target the step prints EXACTLY ONE line and nothing runs on this machine, for example
`runtime mode: no execution target (the host ci-box is named by the repository's config file but you have not allowed it: add it to
$DEAD_CODE_CHECKER_RUNTIME_HOSTS (comma-separated) or pass --host ci-box)` (code `dc.runtime-skipped`, level I). The tool has no local
execution path at all.

### The ssh form

The tool starts the system `ssh` and nothing else, with `-o BatchMode=yes -o StrictHostKeyChecking=yes -o ClearAllForwardings=yes -o
ForwardAgent=no -o ForwardX11=no -o PermitLocalCommand=no -o ControlMaster=no -o ControlPath=none -o RemoteCommand=none -o
RequestTTY=no`, keep-alive and connect-timeout options, `-p PORT` and `-l USER` when you gave them (`--port`, `--user`, or your entry in the list), then `-- HOST` and one fixed remote
command. Your own ssh configuration still names aliases and keys, but it cannot start a local command, forward a port or an agent, or
share a connection. There are four remote commands, one fixed form each, built only from validated parts (32 and 64 hex digits and
fixed names): *put*, *run*, *pull* and *cleanup*. Transfers are tar over the same ssh channel (no `scp`, `rsync` or `sftp`).

- *put* makes a private directory (mode 0700, below a private `/tmp/.dcc-rt-<uid>` that is refused when it is a link or belongs to
  somebody else) for this run, which must not exist, writes the tar from standard input, and takes exactly five members out of it:
  `in.tar` (the project delivery) and the tool's own `rtbox.py`, `runtime.json` and `tracers/py/sitecustomize.py`.
- *run* first checks the sha256 of those three tool files against the ones sent, then starts `python3 -I rtbox.py --on-target --box DIR
  --sha256 HEX` under `env -i` with `PATH`, a private `HOME` and `TMPDIR` inside the run directory, `LANG` and nothing else, behind a
  wrapper that ends the whole process group when the ssh channel closes (a timeout here, a dropped connection).
- *pull* sends back a tar of exactly `manifest.json` and `runtime.json`; *cleanup* removes the run directory. Cleanup runs after every
  started run, also a failed one.

### What is sent, and what comes back

What leaves this machine is the tracked files of the repository at `HEAD`, as git's object store has them (no work tree: an uncommitted
edit, an untracked file and anything in `.gitignore` never go), with the same modes, and the tool's own box files. Symbolic links that
leave the tree, files over 16 MB and submodules are left out (with a note); a tree over 256 MB or 100000 files is not sent. A tracked file
whose name looks like a credential (`.env*`, `*.pem`, `*.key`, `id_*`, `.ssh/`, `.npmrc`, kubeconfig files and the like; template names such
as `.env.example` are fine) or whose content matches a secret rule (private keys, cloud and platform tokens, quoted `password = "..."`
assignments, also inside zip, tar, gzip, bzip2 and xz members) stops the copy before anything is sent; the message names the file and
the rule, never the text.

What comes back is parsed as data against what was sent: exactly the two files, size caps, a manifest with the run id, commit, size and
sha256 of `runtime.json`, then a strict schema (every file and blob id must be one that was sent, every row has exactly its keys and
whole numbers). Texts from the target are cut to one short line and masked for secret-looking parts. Anything that fails is one
`dc.runtime-failed` warning and nothing is stored. A target without a working sandbox answers `no sandbox`: one skip line.

### Stored runs and `graph check`

A good run is stored in `<data dir>/projects/<name>-<hash>/runtime/<utc>-<head8>/` as `runtime.json` and `report.md`; the newest five
are kept. It is not one of the run directories of `check`, so `prune` and the overview page ignore it.

`graph check` (branch and repo level) reads the newest stored run of the project when there is one; with none, nothing changes. It never
contacts the target and never starts a run. A dead or dead-cluster claim about a symbol that ran (or about a member of a dead cluster one of
which ran: such a cluster has an entry the graph does not see) is replaced by the level I finding
`dc.alive-runtime`, which names the run (never an error or a warning). A file that changed since the run is not used (its lines moved)
and is counted in `meta.runtime`. The run also feeds the confidence of the remaining claims: a claim about a symbol that ran loses 40
points, one about a symbol of a covered file that never ran gains 10 (`graph/data/confidence.json`); no level or code changes. A stored run
older than `refresh_days` is still used, and one level I `dc.runtime-stale` finding says so.

### Codes

| Code | Level | Meaning |
| --- | --- | --- |
| `dc.alive-runtime` | I | a dead claim about a symbol that ran, withdrawn; names the stored run |
| `dc.runtime-skipped` | I | no usable target (no host, not allowed, this machine, unknown host key, no sandbox, no language with a tracer, nothing to copy) |
| `dc.runtime-failed` | W | the target answered and the command or the delivery failed, or the copy was stopped by a secret check |
| `dc.runtime-stale` | I | the stored run is older than `refresh_days`; it is still used |

### Execution checks of a fix

The same target and the same delivery serve the executing checks of a verified fix (tests, build scripts): a check run is the tracked files
at `HEAD` with the patched texts over them, the command once per package directory, and back come the exit code and the first error line.
`runtime.exec_target(root)` gives that target (or the reason there is none); the rules above are the same.

## Fix: the removal patch and `--verify`

```console
$ dead-code-checker graph fix --dry-run [--scope branch|repo] [--code CODE]... [--path GLOB]... [--root DIR] [--base REF]
                                        [--verify [--host HOST [--user USER] [--port N]]] [--min-confidence N] [--jobs N] [--json]
```

`fix --dry-run` prints, on standard output, a unified diff for review (`git apply` and `patch -p1` take it) that removes the dead
symbols a check has confirmed. The summary goes to standard error. The command never writes the work tree, never stages and never
commits; without `--dry-run` it stops with exit 2 (`only --dry-run is supported`). The scopes are those of `check`: `branch` (the
findings of `check --scope branch`, `--base` as there) and `repo` (the whole tree as the repo level sees it: every file counts as
added). `--code` keeps the findings of the given codes, `--path` the files that match a glob or lie under a directory.

What is cut. A Python function, method or class named by a `dc.dead`, `dc.dead-cluster` or `dc.introduced-dead` finding that an
index or an engine corroborates. A claim that nothing corroborates is a suspect and is never removable; the summary counts those
(`skipped N: not corroborated`). Each span is checked against the file before it is cut (the file must parse, a definition with the
same first line, last line and name must be there); decorators and the comment lines directly above a definition go with it, the blank
lines around the hole are tidied, and a removal that would leave an empty block is tried alone and, if it still breaks the file,
listed as manual. Everything else is listed as manual with the reason and never guessed: another language, a changed file, a symlink,
a symbol that is not at the line of the graph.

Confidence. Every claim has a number (`graph.confidence`). The files of the patch and the lists of removed and manual symbols go the
surest first (confidence, then path and line); `--json` has `"confidence"` per symbol. `--min-confidence N` removes only claims of at
least `N` and skips the others with that reason; a claim with no number is skipped too, because a floor is a promise. Without the flag
nothing is dropped.

`--verify` checks the removals before they are offered. The patch is applied to a copy of the tree (the files git lists, without
secret-looking names; symlinks that are absolute or leave the tree are not copied) and, per language, the cheapest check that can
show a removal unsafe runs on it. There are two classes of check, and the line between them is the trust rule:

- Local checks never execute project code. They compile or type-check and run nothing: Python (`py-compile+names+imports`:
  `compile()`, `symtable` and `ast` of the patched files and an import scan of the tree, star imports and `__all__` included, run by
  `graph/pycheck.py` as a separate `python3 -I` process in a bubblewrap box, or in the checker's own process with a note when the host
  has no box; it never imports, runs or evals what it reads), Go (`go vet ./...`, offline) and TypeScript (`tsc --noEmit`). The two
  toolchain checks run only inside the box (no network, a cleared environment, a private home, only their scratch directories
  writable); without bubblewrap they are not run and the removal is `unverified` with that reason. The list of commands that may run
  as a local check is a constant in the code (`go vet`, `go build`, `tsc --noEmit`); the data file cannot widen it.
- Executing checks (the tests of the project, `cargo check`, `mvn`, `gradle`, `npm test`) run only on a configured remote execution
  target, never on this machine. `--host HOST` names the ssh host of `[graph.runtime]` (it must be on the allow-list
  `$DEAD_CODE_CHECKER_RUNTIME_HOSTS`), `--user` and `--port` its login. With no target the executing step is skipped and the report carries one line,
  `runtime mode: no execution target (<why>)`; the symbols stay at what the local check said.

Statuses, one per symbol: `verified-local` (the local check passed; no target or no executing check), `verified-runtime` (the check
on the target passed), `unverified` (no check could judge it: none for the language, no box, the tool is missing, or the check fails on
the tree as it is; the removal stays in the patch, with the reason) and `failed` (the check broke on it, or it could not be shown to
pass after the whole patch broke: dropped from the patch, with the first error line of the check, secrets in it masked). A symbol
inside a removed one has the status of its removal.

The bounded search. Round 0 checks the whole patch (and, for a check that can fail on its own, the tree as it is: a check that fails
there judges nothing). When the whole patch fails, round 1 checks the removals of each file alone, round 2 those of a file that still
fails one symbol at a time, and the survivors are then checked together; if they fail together a binary search over their order finds
the first removal that breaks them, drops it and goes on. `data/fix.json` bounds rounds and checks per class; what is not proven when
the bounds are spent is dropped, never kept. The runs of a round are parallel (`graph.par`, threads), and the result, the order of
the rows and the patch are the same for any worker count (`--jobs`).

What is never done: the work tree is not written (the copies live in a private temporary directory that is deleted afterwards);
nothing is staged or committed; nothing of the project is executed on this machine (a local check is non-executing, an executing one
goes to the target); nothing is downloaded; `fix` writes no run folder and no pages; a claim that is a suspect is not removed.
